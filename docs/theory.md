# Расчёты: можно ли сделать ToF-камеру из OV7670 + подсветка монитора

Документ содержит оценки, на которых держатся выводы эксперимента
`004_rolling_shutter`. Все числа — из datasheet OV7670 v1.4, измерений
симуляции (модель камеры) и базовой физики; ничего не выдумано.

## 1. Тайминг камеры

Обозначения: `f_frame` — частота кадров, `N` — полное число строк кадра
(включая blanking), `f_line = N·f_frame`, `T_row = 1/f_line`, `T_exp` —
время экспозиции строки.

| Величина | Формула | Значение (30 к/с) |
|---|---|---|
| `T_frame` | 1/`f_frame` | 33.3 мс |
| `f_line` | N·`f_frame` | ~15.3 кГц (N=510) / 15.75 кГц (N=525) |
| `T_row` | 1/`f_line` | ~65 мкс |

**Факт из этого эксперимента:** в 001/002 XCLK камеры формируется toggle-FF,
поэтому `XCLK_DIV=2` даёт **sys/4 = 12.5 МГц**, а не 25 МГц (как написано в
`001/docs/clocking.md`). Все оценки ниже используют `T_row` по **измеренному**
PCLK, а не «25 МГц из комментария».

### 1.1 Лестница скоростей XCLK (12.5 → 25 МГц)

XCLK формирует модуль `rtl/xclk_gen.sv`:

```text
f_xclk = f_sys / (2·XCLK_DIV),   f_sys = 50 МГц,   скважность ровно 50 %
```

| `XCLK_DIV` | `f_xclk` | Комментарий |
|---|---|---|
| 1 | **25.00 МГц** | быстрый режим: вдвое больше пикселей в секунду |
| 2 | 12.50 МГц | по умолчанию: заведомо в пределах datasheet OV7670 |
| 3 | 8.33 МГц | если камера нестабильна на 25 МГц |

PLL не нужен: деление на 2 даёт ровно 25.000 МГц (фронты равномерные,
дрожания нет). PLL понадобился бы только для «канонических» 24.0 МГц.

Что даёт удвоение XCLK (при том же числе строк и пикселей в кадре):

* пропускная способность (пикселей в секунду) — **×2**; фактический
  `f_frame` зависит ещё и от внутренних таймеров сенсора, поэтому его надо
  **измерить** по `cycles` в заголовке `F` (не предполагать);
* `T_row` и `T_px` — **÷2**, значит полоса света измеряется вдвое точнее
  по времени (дискретность задержки строба при этом остаётся 20 нс —
  она задаётся системным клоком);
* чувствительность «задержка строба → номер строки» удваивается
  (`Δrow = Δdelay / T_row`): чтобы сдвинуть полосу на одну строку, нужна
  вдвое меньшая задержка — в тесте шаг свипа равен 320 системным тактам
  вместо 640;
* ресурсы и логика **не меняются** — весь пиксельный тракт синхронен PCLK,
  а CDC те же (см. `README.md`, раздел CDC).

Ограничение: datasheet OV7670 указывает XCLK ≤ 24 МГц, поэтому 25 МГц —
разгон на 4 %. Он проверен только в симуляции (`tb_top_rolling_shutter`
прогоняется дважды — при 12.5 и 25 МГц); на железе при артефактах
изображения надо вернуться на `XCLK_DIV=2` (или 3).

### 1.2 Сколько света проходит между соседними пикселями

Свет за время между соседними пикселями/строками/кадрами проходит
`d = c·T`, `c = 299 792 458 м/с`. Для VGA 640×480 при 30 к/с
(`T_frame` = 33.3 мс, 525 строк, `T_row` = 63.5 мкс):

| Интервал | Время | Путь света | При XCLK вдвое выше (60 к/с) |
|---|---|---|---|
| пиксель | ~99 нс | **~30 м** | ~50 нс → ~15 м |
| строка | 63.5 мкс | **~19 км** | 31.8 мкс → ~9.5 км |
| кадр | 33.3 мс | **~10 000 км** | 16.7 мс → ~5 000 км |

Точные числа для конкретного дампа считает `scripts/parse_profile.py`:
он берёт `lines`/`px`/`cycles` из заголовка `F` и печатает `T_frame`,
`f_frame`, `T_row`, `T_px` и путь света за пиксель / строку / кадр.
Для модели камеры в симуляции (24 строки × 16 пикселей, XCLK 12.5 МГц)
кадр = 311 мкс, строка = 13.0 мкс, пиксель = 810 нс — то есть ~93 км за
кадр, ~3.9 км за строку и ~240 м за пиксель.

Практический вывод: «дальность по положению полосы» получается
**километровой**, а не сантиметровой — именно поэтому прямой ToF на
OV7670 невозможен (§2), а измерять имеет смысл только `T_row` и
построчное поведение сенсора.

### 1.3 Разрешение кадра: что меняется

Кадр задаётся параметром `CAM_SIZE` (см. `README.md`, «Разрешение кадра»).
Для измерительного тракта важны четыре следствия:

| Режим | `px` в строке | Байт YUV в строке | Строк | Ч/б-кадр | Строк `B` в дампе |
|---|---|---|---|---|---|
| QQVGA 160×120 (`CAM_SIZE=1`) | 160 | 320 | 120 | 2400 Б (3 M9K) | 300 |
| QVGA 320×240 (`CAM_SIZE=0`) | 320 | 640 | 240 | 9600 Б (9 M9K) | 1200 |
| VGA 640×480 (`CAM_SIZE=2`) | 640 | 1280 | 480 | 38400 Б (34 M9K — не влезает) | 4800 |

1. **`T_row` растёт вместе с числом пикселей.** `T_row = px / f_pclk`
   (с точностью до blanking), поэтому при том же XCLK строка QVGA примерно
   вдвое длиннее строки QQVGA. Это прямо видно в заголовке `F`: `cycles`
   для QVGA ≈ вдвое больше, если сенсор не меняет внутренние таймеры.
   Точное значение — **измерить** (`cycles/lines`), а не предполагать:
   в QQVGA таблица включает делитель PCLK (`COM14=0x1A`), так что `f_pclk`
   там не обязан быть таким же, как в QVGA.
2. **Дискретность по времени на пиксель падает.** `T_px = T_row / px`
   (для QVGA при 30 к/с ≈ 63.5 мкс / 320 ≈ 200 нс), поэтому путь света за
   пиксель в QVGA вдвое короче — та же логика, что и при удвоении XCLK
   (§1.1), только «бесплатно» по частоте.
3. **Кромка полосы.** QQVGA получается из VGA включением DCW-делителя
   на 4 (`COM3`, `COM14`, `DCWCTR`), QVGA — внутренним режимом сенсора
   (`COM7` бит 4). Это разные пути обработки, и кромка световой полосы
   может быть разной по «мягкости». Гипотеза для проверки на железе:
   у QQVGA кромка мягче (пиксель формируется из группы соседних), у QVGA
   резче; количественно — по числу строк с промежуточной яркостью между
   тёмным и светлым уровнем (`parse_profile.py` печатает границы полосы).
4. **Дамп и память.** Выгрузка `B` растёт линейно: 1200 строк по 8 байт
   для QVGA — это ~26 КБ текста и ~2.5 с на 115200 бод (против 0.6 с в
   QQVGA). Память ч/б-кадра: 9600 Б ≈ 9 из 30 блоков M9K.

## 2. Прямой (direct) ToF

Строка сенсора — это временное окно длиной `T_row`; измеряя положение
световой полосы, получаем дальность с дискретностью

```text
δd = c·T_row/2 ≈ 0.3 м/нс · 65 мкс / 2 ≈ 9.8 км
```

Субстрочная интерполяция по 8 битам делит это на 256 → ~38 м; по 12 битам →
~2.4 м. Сантиметры потребовали бы затвора ~70 пс — OV7670 так не умеет
(минимум — экспозиция в 1 строку).

**Вывод: direct ToF на OV7670 невозможен.**

## 3. Косвенный (AMCW / iToF) — модуляция света

Дальность и фаза:

```text
d      = c·φ / (4π·f_mod)
d_max  = c / (2·f_mod)              (однозначность по фазе)
φ(1 м) = 4π·f_mod/c
```

Контраст модуляции при интегрировании за экспозицию (прямоугольное окно):

```text
C = sinc(π·f_mod·T_exp)
```

| `f_mod` | `d_max` | `φ` на 1 м | контраст `C` при `T_exp=65 мкс` | вывод |
|---|---|---|---|---|
| 30 Гц | 5000 км | 1.3·10⁻⁶ рад | ~1.00 | фаза не различима |
| 480 Гц | 312 км | 2.0·10⁻⁵ рад | ~1.00 | то же |
| 8 кГц | 18.8 км | 3.4·10⁻⁴ рад | 0.61 | предел контраста |
| 15.3 кГц | 9.8 км | 6.4·10⁻⁴ рад | **0 (нуль)** | синхронный ноль |
| 1 МГц | 150 м | 0.042 рад | 0.005 | контраст < шума |
| 10 МГц | 15 м | 0.42 рад | 0.0005 | невидимо |

Шум дальности (shot-noise, `N_ph` — число фотоэлектронов):

```text
σ_d ≈ c·T_exp / (4·m·√N_ph)
```

При `T_exp = 65 мкс`, `N_ph = 10⁴`, `m = 1` → **σ_d ≈ 49 м**; даже при
`N_ph = 10⁸` → ~0.5 м. Сантиметры требуют `T_exp` порядка десятков нс.

**Вывод: AMCW-ToF на OV7670 невозможен** — экспозиция не может быть короче
строки, а фаза при такой экспозиции не наблюдаема.

## 4. Почему подсветка монитора не подходит как излучатель ToF

| Способ модуляции | Реальная частота | `d_max` | оценка |
|---|---|---|---|
| Контент экрана (белый/чёрный, 60 Гц) | ≤ ~30–60 Гц | 5000 км | только структурированный свет |
| PWM подсветки LED | 200 Гц…20 кГц | 7.5 км @20 кГц | для ToF не годится |
| Ответ LCD-панели | 5–20 мс → ≤50–100 Гц | — | ограничивает контентную модуляцию |
| Внешний LED/лазер + MOSFET | до МГц | 150 м @1 МГц | единственный быстрый источник |

Дополнительно: подсветка — высоковольтная LED-линейка (десятки вольт,
сотни мА), её нельзя «подключить к 3.3 В GPIO» без вскрытия монитора и
MosFET/драйвера; в проекте такого источника нет.

В проекте единственный управляемый дисплей — TFT-модуль из эксперимента
`003` (240×320, подсветка на PIN_144 как обычный GPIO). Это дешёвый
**структурированный** источник, но не ToF.

## 5. Что всё-таки можно измерить (и зачем этот эксперимент)

Инструмент, реализованный в 004, измеряет то, что физически доступно:

1. **Тайминг камеры**: `f_frame`, число строк, пикселей в строке (`T_row`).
2. **Время строки по положению полосы**: задержка строба увеличивается на
   `T_row` → полоса смещается ровно на одну строку (проверяется в L3-тесте
   и будет проверено на железе).
3. **Контраст модуляции** — верхняя граница любого ToF-метода на этом сенсоре.

Именно эти измерения и есть ответ на вопрос «можно ли сделать ToF»: **нельзя**,
потому что экспозиция OV7670 не короче строки, а фаза модуляции при такой
экспозиции неотличима от нуля.

## 6. Реалистичные продолжения (для задачи «мешки на конвейере»)

| Путь | Что даёт | Примечание |
|---|---|---|
| Структурированный свет (TFT как проектор, Gray code / фазовый сдвиг) | карта глубины | не ToF, но глубина реальна; 60 Гц → ~7.5 3D-кадров/с |
| Лазерная триангуляция (линейный лазер + OV7670) | профиль высоты | устойчиво на конвейере, дешевле |
| Внешний ToF-сенсор (VL53L1X / VL53L5CX / TMF8801) по I²C | настоящая дальность | 4 м, зоны; I²C на свободных 112/113 |
| Две камеры + стерео | глубина по диспаратности | совпадает с исходным планом на 2 камеры |
| USB-камера на хосте | всё распознавание на ПК | FPGA выпадает из контура зрения |

Для **подсчёта** мешков ToF не нужен: достаточно 2D-кадра + триггер/энкодер
ленты. Глубина нужна только для объёма/высоты.

## 7. 1 бит против 8 бит: что даёт чёрно-белое изображение

В проекте камера работает в YUV-режиме: по DVP идёт 2 байта на пиксель
(Y + CbCr), а FPGA оставляет **только Y** — то есть в логике уже 1 байт на
пиксель, а не 2. «Чёрно-белое» (1 бит) получается дополнительным порогом
(`rtl/luma_threshold.sv`).

| Что даёт 1 бит | Что теряется |
|----------------|---------------|
| кадр 160×120 = 2400 байт (2.4 КБ) вместо 19.2 КБ → в 4 МБ SDRAM влезает ~1700 кадров вместо ~220 | точность положения фронта: после порога остаются только целые «0/1», а суб-LSB информация (доли LSB на границе полосы) теряется |
| морфология = AND/OR в окне (чистая логика, без делителей), бинарная связность и run-length — почти бесплатно | классификация по цвету (для неё нужен RGB565/YUV целиком) |
| компактный «golden reference»: однозначный артефакт для регрессии | тонкая градация яркости (для измерения контраста полосы 8 бит лучше) |
| устойчивость к общему уровню освещения (если порог адаптивный) | — |

**Правило для нашей задачи:** измерять *положение* полосы нужно по 8-битному
профилю (взвешенный центроид по фронту даёт точность лучше строки); 1 бит
полезен как **детектор** (где вообще что-то изменилось), как **маска** для
последующей обработки и как **компактный артефакт**.

В сценарии модулируемого освещения (раздел 3) контраст полосы — доли
процента, то есть 1–2 LSB: там 8-битные значения являются **единственной**
информацией, и бинаризация фиксированным порогом превращает сигнал в шум.
Адаптивный порог `(min+max)/2` переживает изменение общего уровня, но не
спасает слабый контраст.

Синергия с настройкой камеры: в проекте AGC/AEC **выключены** (SCCB-таблица
1) — яркость сцены стабильна, поэтому фиксированный порог осмыслен (иначе
пришлось бы пересчитывать его каждый кадр).
